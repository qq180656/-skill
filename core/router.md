# Agent 路由逻辑 (Router)

## 1. 入口信号识别

Agent 接收到用户输入后，执行以下判定流程，将输入归入唯一路径。

### 判定算法

```
INPUT: user_message
OUTPUT: route_path ∈ {A, B, C, EDIT, ERROR}

STEP 0: 优先级判定（当输入同时含脚本和Brief时）
  CONDITION: 用户消息既包含脚本片段（>20字的结构化口播），又包含需求说明文字
  SUB-JUDGE: 判断脚本片段完整性 + 用户意图
    - **新创作意图优先**：若需求明确要"新做/再做N条/别重复已有/换新场景钩子"，则所给脚本是**风格/合规参考样本**（非生产对象）→ route_path = B（参考样本作为 CREATIVE_DESIGN 的风格输入，绝不把旧脚本原样再生产一遍）
    - 完整脚本（有开头有结尾、覆盖全片口播、>50字）且无新创作意图 → 需求说明仅作为元信息（产品名/类型/数量），按 STEP 1 走路径A
    - 部分片段（仅覆盖某一段/某一句、无完整结构）→ route_path = C（混合输入）

STEP 1: 检查是否包含完整脚本
  CONDITION: 用户消息中包含逐段画面描述、分镜表、带角色台词的完整剧本，
             或含时间轴的逐段口播文案（>50字的结构化文本）
  MATCH → route_path = A

STEP 2: 检查是否为项目/需求指令
  CONDITION: 用户消息为简短指令，如"我要好医保中老年的前贴"或"做好医保门诊险的成片"
  MATCH → route_path = B

STEP 3: 检查是否为修改/追加指令
  CONDITION: 用户要求修改已有产物（换镜头/改台词/调风格/改字幕/换BGM）——产物可在上下文中，**也可仅存在于磁盘**（`_task_ids.jsonl`/交付目录，如"昨天那条视频把第二句字幕改一下"）；agent 应先按 wf_edit.md Step1 从磁盘定位，**不因产物不在上下文就误判为新建**。带完整新脚本的"脚本级"修改仍属 EDIT，不要因含脚本就抢到 STEP 1
  MATCH → route_path = EDIT (走 wf_edit.md；状态机见 state_machine.md §5 的 EDIT 回边)

STEP 4: 兜底
  DEFAULT → route_path = B (按 Brief 驱动处理，先补齐信息再创作)
```

## 2. 路径定义

### 路径 A: 完整脚本直入 (entry_direct_script.md)

**适用场景**: 用户直接粘贴或上传了包含口播文案的完整脚本（可能含括号警示语，也可能不含）。

**Agent 行为**:
1. 不重新创作脚本，直接对现有脚本进行**原子化拆解**。
2. 执行 TTS 发音优化（断句、空格注入、删除级词删除）。
3. 执行合规校验（禁用词扫描、警示语挂载）。
4. 进入视频生成阶段。

**关键约束**:
- 禁止重写、精简或合并用户脚本中的台词。
- 警示语如用户脚本中已包含，直接提取；如未包含，根据 `knowledge/compliance/` 中的规则自动补挂。
- 用户说"前贴" → 每条脚本时长目标 15s；说"成片" → 根据内容量弹性定时长。

### 路径 B: Brief/需求驱动 (entry_brief_only.md)

**适用场景**: 用户只给了项目名和类型（如"我要好医保中老年的前贴"），没有脚本。

**Agent 行为**:
1. 读取 `knowledge/compliance/` 中的产品合规规则。
2. 读取 `knowledge/video_parameters/` 中的语速、时长、模型参数。
3. 撰写脚本（含警示语标注）。
4. 对脚本进行**原子化拆解** + TTS 优化 + 合规校验。
5. 进入视频生成阶段。

**关键约束**:
- 撰写脚本前必须确认前贴 vs 成片（时长不同）。
- 必须过三层合规规则叠加。
- 脚本产出后需用户确认再进入生成阶段。

### 路径 C: 混合输入 (entry_mixed.md)

**适用场景**: 用户同时提供了部分脚本片段和部分需求说明，如"做好医保中老年的成片，开头要讲0免赔，中间讲报销比例，最后加一句投保链接。脚本参考以下片段：好医保中老年长期医疗..."

**Agent 行为**:
1. 从脚本片段中提取已确定的内容（口播文本、可能的警示语）。
2. 从需求说明中提取未覆盖的部分（缺失的场景、台词、情绪）。
3. 合并两部分信息，补齐缺失内容，生成完整脚本。
4. 进入路径A的原子化拆解流程。

**关键约束**:
- 用户已提供的脚本片段不修改，仅补齐缺失部分。
- 补齐内容需过三层合规规则叠加。
- 合并后的完整脚本需用户确认再进入生成阶段。

### 路径 EDIT: 修改指令 (wf_edit.md)

**适用场景**: 用户对已有产物提出修改（换镜头/改台词/调风格/加字幕/换BGM等）。

**Agent 行为**:
- 先按 `wf_edit.md` 的修改类型判定表，确定修改属于音频级/字幕级/镜头级/台词级/脚本级
- 音频级/字幕级（保留式修改）→ 直接执行，不需重新生成视频
- 镜头级/台词级 → 仅重做受影响部分，KEEP 的镜头复用原文件
- 脚本级（重做式修改，如换题材/重写脚本）→ 回到路径 A 或 B 重走全链路
- 所有修改完成后必须重跑受影响的校验项

## 3. 分流后公共执行链

无论路径 A 还是 B，脚本就绪后都进入以下公共链路：

```
脚本就绪 (Atomic Scripts)
    │
    ▼
┌─────────────────────────────────────┐
│ STORYBOARD → ASSET_PREP → READY → GENERATING → VERIFYING → DELIVERING → DONE │
└─────────────────────────────────────┘
```

具体执行逻辑见 `workflows/` 下各子流程文档。

> ⚠️ 上图为"脚本就绪（PLANNING 产出 Atomic Scripts）后"的分流速览。**完整主干状态序列（INPUT_PARSE → CREATIVE_DESIGN → PLANNING → STORYBOARD → ASSET_PREP → READY → GENERATING → VERIFYING → DELIVERING → DONE）与所有状态转移，以 `core/state_machine.md` 为唯一权威**；README 与本文的流程图仅作导航，如有出入以状态机为准。
